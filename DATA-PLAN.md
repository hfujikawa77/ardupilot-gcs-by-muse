## Tested sources
### ArduPilot SITL — MAVLink over TCP 127.0.0.1:5760 (the live data + command channel)
**Used by**: server actions in `server/src/actions.ts` (a singleton MAVLink client held in the actions worker: `getStatus`, `connect`/`disconnect`, `setMode`, `arm`, `takeoff`, `land`, `rtl`, `guidedGoto`, `setJoystick`)
**Test command**: started the built binary `~/workspace/ardupilot/build/sitl/bin/arducopter -S --model + --speedup 1 --defaults Tools/autotest/default_params/copter.parm` (listening on 0.0.0.0:5760 confirmed via `ss -ltn`), then ran a pymavlink probe (`~/venv-ardupilot`): `mavutil.mavlink_connection('tcp:127.0.0.1:5760')`, `request_data_stream(MAV_DATA_STREAM_ALL, 4Hz)`, plus `set_mode('GUIDED')`
**Sample output**: `HEARTBEAT type=2 autopilot=3 mode=STABILIZE armed=False`; ATTITUDE roll≈0.0001 pitch≈0 yaw≈-0.346; VFR_HUD heading=340 throttle=0; SYS_STATUS voltage_battery=12600 battery_remaining=100; GPS_RAW_INT fix_type=0 lat/lon=0 at cold start (SITL GPS locks after warm-up; default SITL home is Canberra); `after GUIDED set: mode=GUIDED` — mode-change commands verified end to end
**Processing**: the server implements MAVLink v1/v2 framing in TypeScript (X.25 CRC + per-message CRC_EXTRA dumped from the installed pymavlink dialect and hard-coded from that evidence: HEARTBEAT 50, SYS_STATUS 124, GPS_RAW_INT 24, ATTITUDE 39, GLOBAL_POSITION_INT 104, VFR_HUD 20, STATUSTEXT 83, COMMAND_ACK 143, COMMAND_LONG 152, SET_MODE 89, MANUAL_CONTROL 243, SET_POSITION_TARGET_GLOBAL_INT 5, REQUEST_DATA_STREAM 148, RC_CHANNELS 118, BATTERY_STATUS 154, HOME_POSITION 104, EKF_STATUS_REPORT 71). Incoming frames update a cached telemetry snapshot (attitude, position, HUD, GPS, battery, mode/armed, RC, EKF flags, STATUSTEXT log, COMMAND_ACK results); the client polls the snapshot. Commands are encoded as SET_MODE / COMMAND_LONG (arm-disarm 400, nav takeoff 22, nav land 21, do reposition via SET_POSITION_TARGET_GLOBAL_INT 86 with position-only type_mask for Guided Goto). Joystick: client posts axes at ~10 Hz while enabled; the server re-sends MANUAL_CONTROL (x=pitch, y=roll, z=throttle 0..1000, r=yaw; ±1000 scale) on a 100 ms timer and forces neutral (0,0,500,0) if client updates go stale >1.5 s or the toggle is switched off.

## Layout revision (2026-11-07 edit)
- User asked: fit everything on one screen, use listboxes for choices, use tabs, follow QGC's layout, and let the Goto destination be specified by tapping the map.
- Layout is now a fixed `100dvh` column with no page scroll: QGC-style top status bar, a full-bleed map with the HUD as a collapsible overlay (plus map-overlay virtual sticks while the joystick is enabled and a tapped-target chip), a tabbed side panel （飛行 / Goto / スティック / テレメトリ / ログ・接続） whose content scrolls internally, and a one-line latest-message strip at the bottom. On phones the map flexes above a fixed-height tab panel.
- Choices are listboxes: flight mode is a `<select>` fed by the server-provided `modes` list (changing it sends the mode command), takeoff altitude and Goto altitude are preset `<select>`s.
- Tap-to-Goto: the vendored HatchMaps control's public handle exposes no click coordinates (verified by inspecting `client/src/assets/hatch-maps.js`: the handle is only `{destroy, selectPlace}` and the internal view component keeps the MapLibre instance in a `selection` object passed as a React prop). MapPanel therefore walks the holder element's React fiber tree (`__reactContainer$…`) to find that `selection.map`, subscribes to its MapLibre `click` event, and reports `lngLat` as the Goto candidate: the tap only sets the target pin and prefills the Goto tab inputs; the vehicle flies only after the explicit two-step confirm in the Goto tab. If the instance cannot be located, tap stays unavailable (the map chip says so) and the Goto tab's numeric inputs plus 現在位置/ホーム quick-fill buttons remain the specification path; the same alternatives are named in the map-unavailable fallback panel.

## Freeze fix (2026-11-07 edit: 「マップもHUDも動かない。離陸、スティック操作しても」)
- Diagnosed live against the bridge (127.0.0.1:8766/status): telemetry was flowing the whole time (rxMsgCount > 255k, lastRxAgoMs ~20 ms). Three distinct causes made the app *look* frozen:
  1. **Map marker was a mount-time snapshot.** The vendored HatchMaps control renders `places` into a static GeoJSON source (`J7(places)` in hatch-maps.js) that nothing updates after mount; MapPanel remounted only on target/home change or after the vehicle moved > 400 m, so during normal short flights the aircraft pin never moved (the panel even labelled it 「ピン位置 … 時点」). Fix: the vehicle is no longer a control place. MapPanel locates the MapLibre instance (the same `selection.map` fiber walk already used for tap-to-Goto, now driven by a 400 ms watchdog that retries indefinitely instead of giving up after 10 s) and maintains its own GeoJSON source `gcs-live` on it: a track LineString plus the vehicle as a symbol layer whose icon is a canvas-drawn triangle registered via `addImage`, rotated by the live heading (`icon-rotate: ["get","heading"]`, `icon-rotation-alignment: "map"`). The source is refreshed with `setData()` whenever the telemetry snapshot changes, and the camera follows the vehicle (easeTo once it drifts > 12 m from center; a user drag or the follow toggle turns follow off; the existing 機体にセンタリング button turns it back on). Home/target remain control places (home never moves; a new target remounts anyway). If the instance never appears within 20 s of a mount, the panel falls back to snapshot pins that remount on a ~25 m grid so the marker still tracks coarsely.
  2. **Sticks are ignored in GUIDED.** Takeoff leaves the vehicle in GUIDED, where ArduCopter does not apply MANUAL_CONTROL at all — stick input was streamed correctly (RC override verified in the earlier build) but the vehicle quite correctly ignored it, with no UI hint. Fix: the client knows the stick-effective modes (STABILIZE / ACRO / ALT_HOLD / LOITER / POSHOLD / DRIFT / SPORT / FLOWHOLD); in any other mode the スティック tab shows a warning naming the current mode plus a one-tap LOITER switch, and while the joystick is on an amber chip over the map offers the same switch.
  3. **Leftover airborne state from verification flights.** The vehicle had been left hovering armed at 10 m in GUIDED (subsequent inspection probes kept re-commanding it: a LAND was overridden by a probe-issued Guided Goto), battery draining 63% → 0%. So for the user, takeoff-to-10 m was a no-op (already there) and the HUD sat level in a stationary hover. Remediation: landed and disarmed via the bridge; the SITL was then restarted so its simulated battery resets to full, leaving a clean on-ground starting state.
- HUD itself needed no change: it renders from the same live snapshot (roll/pitch/heading), which the user confirmed recovered once the vehicle actually manoeuvred.

## Stick fix, round 2 (2026-11-07 edit: 「スティックが反応しません。GOTOは期待どおりになりました」)
- Re-diagnosed the whole stick path live before changing anything. Bridge level is healthy: `POST /joystick {pitch:1}` from curl moved RC channels to `[1500, 1000, 1500, 1500]` with `joyStreaming: true`, and a full bridge-driven flight (takeoff → LOITER → full forward pitch) produced pitch −28.6°, groundspeed 8–9 m/s and ~35 m of travel, then clean LAND/disarm. Page level is also healthy: driving the built page with the audit probe, toggling the スティック tab's switch ON made the bridge report `joyEnabled/joyStreaming: true` and the neutral MANUAL_CONTROL stream reached the vehicle (RC `[1500, 1500, 1500, 1500]`).
- The remaining trap is the mode gate: the user's confirmed flow is takeoff (→ GUIDED) and Goto (GUIDED), and ArduCopter ignores MANUAL_CONTROL in GUIDED, so the sticks stream correctly yet the vehicle never reacts — the previous round's only remedy was a passive warning chip / tab button the user had to notice and tap. Fix: enabling the joystick now auto-switches the flight mode to LOITER whenever the current mode is not stick-effective (STABILIZE / ACRO / ALT_HOLD / LOITER / POSHOLD / DRIFT / SPORT / FLOWHOLD), with a status message explaining the switch; the スティック tab copy documents this. The warning chip remains for mode changes that happen *after* enabling (e.g. a failsafe RTL). The stick overlays also got `zIndex: 6` so they always sit above the map's follow toggle (zIndex 5) at the bottom-left corner.
- Vehicle left clean after testing: joystick off (neutral frame sent), landed, disarmed.

## Stick fix, round 3 (2026-11-07 edit: 「やはりスティック操作がちゃんと飛んでないように見える。反応しないし、コマンドが遅延してるような」) + slide-to-confirm
- Measured the layers separately. Bridge direct: `POST /joystick` ≈ 1–3 ms, and an 8 Hz direct stream drives RC (CH2 1100 at pitch 0.8) with `joyStreaming: true`. Through the artifact's action layer a single `setJoystick` round trip took ~4 s (cold privileged channel). The client, however, fired `setJoystick` every 120 ms fire-and-forget, so stick positions queued up unboundedly and reached the bridge seconds late in stale FIFO order; whenever the queue starved, the bridge's 1.5 s staleness failsafe neutralised the stream — the vehicle barely reacted and commands played out seconds after the user let go. That mismatch (fast bridge, slow channel, naive sender) is the root cause; mode gating was already handled in round 2.
- Client fix (App.tsx): single-flight latest-wins sender. At most one `setJoystick` request is in flight and it always carries the newest axes; completion immediately sends any newer state; an idle heartbeat (~2 s) keeps the bridge stream fresh; stick movement pumps immediately; the OFF state goes through the same single-flight path so a disable can never be overtaken by an older enable. Deflection latency is now bounded by one round trip.
- Bridge fix (mav_bridge.py): stream rate 10 Hz → 20 Hz; freshness window 1.5 s → 4 s (matched to the measured channel latency, still failsafe); while enabled it now ALWAYS sends a frame — fresh axes or NEUTRAL — so a stall holds a hover instead of handing the vehicle back to idle RC defaults (throttle 1000); 30 s of silence auto-disables the joystick with a log line. The running bridge had to be restarted for this (killed the old pid; the privileged handler auto-started the new code, and a fresh SITL came up with it, battery back to 100%).
- Bridge-level verification with the new code (live flight): takeoff → LOITER → ONE pitch-0.8 post with no refresh: RC CH2 1100, pitch −20.2°, groundspeed 5.6 m/s, 11.6 m travelled, `joyStreaming: true` for the whole 4 s window. After the window: `joyStreaming: false`, RC all-1500 neutral (throttle 1500, not idle 1000), altitude held (6.4 m → 6.4 m), groundspeed ~0 — safe hover. Then disable + LAND + auto-disarm, battery 93%. (Altitude settled from 10 m to 6.4 m during the first seconds of LOITER stick flight, then held; noted, not part of this fix.)
- Slide-to-confirm (same edit, added user request): the two-press ConfirmButton is replaced by a QGC-style `SlideConfirm` — drag the thumb to the right end (≥92%) and the command fires in that one action; releasing early springs it back and sends nothing; keyboard arrows work on the focused thumb. Applied to ARM (danger styling), takeoff, LAND, and the Goto execute control. RTL and DISARM remain plain buttons (safe-direction commands).

## Stick fix, round 3b + map asks (2026-11-07, same edit session)
- Page-level proof for the sender redesign, measured against the live bridge while driving the built page in the audit probe: after toggling the sticks ON in the page, `joyStreaming` stayed True continuously for 22+ s with `joyUpdatedAgoMs` between 53 ms and 631 ms, and the page's auto-LOITER switch fired. This required one more channel: in the audit browser the page's plain timers are throttled hard, so the design now has three delivery paths — (1) single-flight latest-wins change sends, (2) a ~2 s heartbeat, (3) the latest stick state piggybacked on the 300 ms `getStatus` poll itself (the poll keeps flowing via focus/visibility refetches even when timers stall), plus a focus/visibilitychange re-send kick. The bridge freshness window is 6 s; the measured poll cadence keeps updates at ~0.05–0.6 s.
- Caveat from verification: leftover probe pages from earlier audit sessions (sticks left ON in their page state) keep re-feeding `enabled: true` to the shared bridge at ~1.3 s cadence, so a bridge-side disable in this sandbox does not stick while those harness pages live. Production has exactly one page, which starts OFF; a page whose bridge-side stream auto-disabled (30 s silence) self-heals by re-sending its ON state, which is the intended behaviour.
- Satellite/aerial tiles: NOT available, by source constraint. The vendored map runtime's style catalog is hard-coded to `default` (light), `dark`, `grayscale`, `canterbury_1_0`, `light-no-labels`, `dark-no-labels`, `empty` (all vector styles served from `external.xx.fbcdn.net/maps/vt/style/<name>/`); the string "satellite" appears nowhere in the 1.3 MB bundle and there is no raster/aerial tile endpoint. Adding a satellite switch would require a different tile source than the platform map runtime provides, so it was not implemented; reported to the user instead.
- Terrain DEM: no DEM/raster-dem tile source exists in the runtime either (MapLibre's bundled `setTerrain` API has no DEM endpoint to feed), and the user explicitly descoped terrain relief. Implemented instead, per the user's vehicle-only spec: an oblique (pitch 55°) view toggle in MapPanel; in oblique view the vehicle leaves the GeoJSON layer and a screen-space SVG overlay draws its ground projection (ellipse marker at the projected lat/lon), a dashed vertical post, the heading-rotated craft polygon floating at `alt × groundScale × sin(pitch)`, and a numeric relative-altitude label. Not visually verifiable in the audit sandbox (map tiles are egress-blocked there); the MapLibre instance APIs used (`project`, `easeTo({pitch})`, `setPitch`) are the same ones already proven in production for click/follow/setData.

## Freeze recurrence + 3D track (2026-11-07 edit: 「表示が変わってない」再発 / 22:15 JST「また固まってる」)
- Timeline check for the 22:15 recurrence: at that minute the bridge+SITL had just been restarted (for the battery reset below) and a test takeoff was rejected by PreArm ("Need Position Estimate", EKF not yet using GPS) — the vehicle sat on the ground in the restart/warm-up state, so part of that report coincides with operator-side restart interference. The structural weakness it exposed stands, though: the page had no way to show *whether* it was alive, and two silent-freeze paths remained:
  1. **Polling could pause invisibly.** The status query used React Query's `refetchInterval` with default background behaviour: inside the shell webview the iframe can lose focus/visibility while the user is still looking at it, which pauses interval refetching and leaves the last snapshot on screen indefinitely — telemetry values (especially a GUIDED hover, or a landed vehicle) then look frozen even though the bridge is fine. Fix: `refetchIntervalInBackground: true` + `refetchOnWindowFocus: true`, a plain 1.5 s backup interval that forces `refetch()`, and focus/visibilitychange refetch kicks.
  2. **No liveness signal on phone widths.** The only continuously changing elements (EKF / last-Rx / msg count) were `hidden lg:inline`. Fix: the status strip now always shows `更新 HH:MM:SS · <rxMsgCount> msg` (re-rendered on a 500 ms local tick from `dataUpdatedAt`); if data ages past 5 s it turns into a red `⚠ 更新停止 N秒` warning, and a permanent 更新 button forces a refetch — or a full page reload when data is > 15 s old (wedged channel recovery).
  3. **Map live layers never self-healed.** If the MapLibre style reloaded (tile/style refetch), the `gcs-live` source/layers/icon vanished while the instance survived; the watchdog kept calling `setData()` on a missing source (no-op) and the marker/track never returned. Fix: every watchdog tick now re-checks `getSource`/`getLayer`/`hasImage` and re-adds whatever is missing (resetting the data-diff cache so geometry is re-pushed).
- Vehicle state cleanup in the same session: the previous verification flight had drained the simulated battery to 0% at 80 m; landed it, restarted bridge + SITL (fresh battery 100%), then flew a profile (takeoff 15 m → Goto → Goto @ 25 m → LAND) leaving a 329-point track and the vehicle landed/disarmed at 78%.

## 3D track (2026-11-07 edit: 「飛行軌跡を実際に飛んだ3Dの軌跡として」)
- The bridge track was lat/lon only; `GLOBAL_POSITION_INT` handling in mav_bridge.py now stores `altM` (relative altitude) per point. The `getStatus` response schema carries `altM` with a zod `.default(0)` so a stale bridge snapshot can never fail the whole poll.
- Rendering (MapPanel): in the flat top-down view the track stays the GeoJSON 2D line (a top-down projection cannot show altitude). In the oblique view the track leaves the GeoJSON layer and the existing screen-space SVG overlay draws it as a true 3D path: each point is projected to its ground position, then lifted by `altM × local px-per-metre × sin(55°)` — the same projection as the vehicle altitude post — and connected as the main lifted polyline; a faint dashed ground projection and vertical posts every ~15th point (where lift > 5 px) make the height readable. Rising from low to high altitude therefore renders as a line climbing diagonally, as requested.
- Verified at the data layer: bridge flight produced 329 track points with altM spanning 0 → 15 → 25 → 0 m. The overlay drawing itself uses the same `map.project` path as the already-confirmed vehicle altitude post; visual confirmation in the audit sandbox depends on map tiles loading there (egress-blocked in some audit runs).

## Long-term data behavior
- **Refresh policy**: telemetry is live-only and never persisted; the client polls `getStatus` every 250 ms while the page is open and the server reconnects to SITL automatically (lazy reconnect on socket close). No cron/refresh triggers.
- **Growth**: the STATUSTEXT/command log is an in-memory ring buffer capped at the latest 100 entries; the map track is capped at the latest 2000 points and clears on reconnect.
- **Ordering**: log newest-first; telemetry is a single latest-value snapshot per message type.
- **Time semantics**: all timestamps are SITL/vehicle-relative (time_boot_ms) plus server receive time rendered viewer-local; no stored user records, so no DB migration beyond the starter schema is needed.

## Rejected approaches
- **Tried**: Python bridge daemon (pymavlink) exposing HTTP on localhost, called by actions via fetch
  **Why rejected**: probe-ctx proved raw TCP MAVLink works directly from the action sandbox, so a separate daemon adds a process-lifecycle problem (nothing in the artifact runtime would keep it alive) for no benefit; MAVLink framing is implemented in the server instead, with CRC extras taken from the verified pymavlink dialect.
- **Tried**: Browser-side WebSocket MAVLink bridge
  **Why rejected**: the sandboxed iframe cannot open raw TCP to the SITL and no WebSocket MAVLink relay exists on this VM; server-side TCP is the only working channel.
- **Imagery not needed**: this is an instrument/control surface — HUD and map are live functional graphics drawn from telemetry, and the request names no photographic subjects.
